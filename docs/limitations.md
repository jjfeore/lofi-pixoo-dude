# Coverage and playback limits

This bridge uses public command hooks and the separate official completion notifier. It has no native pet renderer integration, transcript reader, app-server attachment, or UI poller. It observes events arriving since startup.

- **Needs input:** PermissionRequest indicates approval processing. Another policy handler may approve it automatically. A matching PostToolUse is evidence of resumed execution, not a general approval-resolution API. Other questions, denied approvals without tool execution, asynchronous user-question tools, and every app waiting state are not fully represented. Terminal events/new prompts clear pending observations. No timeout guesses that an unanswered question was resolved.
- **Completion:** Codex `notify` with `agent-turn-complete` supplies the terminal reaction. `Stop` can cause continuation and is not used as success. The notifier doesn't provide every richer app-server completion status. A main Interrupt provides its own reaction; an idle chat or child cancellation has different coverage.
- **Delegation:** Child identifiers are tracked as observations. SubagentStop is a stop checkpoint and can be followed by continuation, so it cannot guarantee the helper has permanently exited. Parent completion clears its observed children. Background helpers and resumed chats may have events the initial bridge missed.
- **Startup and crashes:** Start the bridge before new work. There is no documented global hook snapshot to replay active chats after a restart. A missed terminal event can leave work visible until a new prompt/session end or bridge restart. Do not infer completion from inactivity. SessionEnd is not guaranteed simply by switching chats.
- **Event order:** Synchronous emitters avoid intentionally reordering events. Metadata has session/turn identifiers and bounded terminal fences, protecting against common delayed old events. This is not a lossless durable event log. The in-memory limits are 1024 sessions, 128 child/approval observations per session and 64 terminal fences per session. A full/unavailable pipe is bounded and cannot hold Codex behind a device request.
- **All local chats:** Global hooks on the host cover observed local chats using those hooks. Cloud work and other computers do not automatically reach the local pipe. A native on-screen pet can remain separately enabled; this bridge doesn't replace the desktop UI object itself.

The default `stored-gif` transport preloads changed native GIFs and selects local filenames for subsequent state changes. With an explicit `device.transport = "frames"`, each change resets and uploads a complete RGB clip through Draw/SendHttpGif. Stable playback has no continuing host frame stream in either mode. The owner verified repeated idle/working recall on this device with instant switches and no visible loading; delegation/one-shot timing still needs its own check. See [stored GIF playback](stored-gifs.md). Playback speed and HTTP transfer speed are independent.

The 40-frame ceiling is a conservative limit informed by community reports, not a vendor guarantee for every firmware. Forty frames at 83 ms is approximately 3.32 seconds per repeated cycle. More frames increase upload duration, memory and loading exposure. Use fewer purposeful frames where possible.

`loop: false`, working/delegation entry, delegation exit and finish/interruption are emulated by a host timer after selection, with an optional calibrated visible-start delay. A reaction returns to the selected base; if no base is supplied, the last supplied frame is held. A non-looping sustained clip similarly holds its final frame. The display may expose loading frames or replay part of a gesture during a slow switch. One-shot timing cannot be frame-perfect without a reliable visible-start signal. It may be better to omit entry/exit clips if your firmware's switching delay is distracting. Remove those references from a separate playback manifest to disable just the transfers; empty mappings for their clip names do not override direct manifest links. Delegation transfers follow the first/last observed child across chats and can be preempted by attention/compaction or replaced by early stop/new-start events.

An unavailable device uses bounded backoff up to 30 seconds. A newer selection replaces older pending work, and partial uploads invalidate the residency cache. One-shots waiting over 10 seconds are dropped so an old reaction is not played on recovery. Brightness changes are retried with uploads only if explicitly configured. These choices favor a responsive current state over replaying every transient event.

Runtime CPU stays low because the bridge blocks on events and lets native loops play. Hook overhead still includes a process launch and a small bounded IPC round trip for each selected hook. Needs-input resumption adds PostToolUse emitters even when no permission is pending. Measure on the target host; Rust does not remove Windows process/shell startup or the Pixoo's loading latency.

Firmware version isn't returned by every model's status commands. A successful upload response verifies acceptance, not visual frame timing or LED appearance. Hardware playback still benefits from direct observation by its owner. See [verification](verification.md) for this host's measured results.
