description: Create or adapt 64x64 pixel art, sprite sheets, and animations into Divoom Pixoo pet packs for the local Codex bridge. Use for characters on black or full scenes with backgrounds, including animation revisions and pack validation.
---

Create portable artwork packs, independent of device credentials or hook installation. The Pixoo receives full 64x64 RGB frames: black pixels are dark; alpha must be composited deliberately. Support character-on-black and full-scene artwork according to the user's choice.

## Base before motion

Read the user's visual direction, reference images, desired clips, and output location. Use available built-in image generation for creative raster work. References supply atmosphere or identity; preserve the user's requested changes. Do not substitute desktop-pet atlas geometry for a Pixoo scene.

Create one square canonical base. Design for a real 64x64 grid with a clear silhouette, broad color regions, and readable props; enlarged fine-detail art alone does not establish suitability. Prepare the output with the bridge's deterministic `prepare` command and inspect both the native 64x64 PNG and its nearest-neighbor preview.

**Show the base and obtain the user's approval before generating the full animation set or sprite sheet.** This project uses a review gate for composition and identity. Explicit prior approval of that base satisfies the gate; silence does not. Revise only the requested aspects and show the revised base when approval is still pending.

## Animation and consistency

Read [references/animation.md](references/animation.md) when authoring motion. Ground every clip in the approved base; keep camera, background, character identity, palette, and prop placement consistent. Prefer short loops and small purposeful changes. Generate raster motion through the available image-generation tool; use deterministic code for resizing, extracting cells, compositing, validation, and previews.

Supported logical selections are `idle`, `working`, `needs-input`, `finished`, `interrupted`, `compacting`, and `delegating`. All are optional. The user can choose other clip names through bridge configuration. `working-enter` is an optional single-play transition linked from `working`. Delegation can reference optional `delegating-start` and `delegating-finished` through its `entry` and `exit` fields. These are transitions for existing lifecycle observations, not additional Codex hooks.

Aim for approximately 12 FPS when requested (`frame_duration_ms: 83`). Use at least 16 frames for short actions and 24-32 frames for idle or working loops. The decker's revised loops and entry/finish use 32 frames; interruption uses forty for its shock, chase and recovery sequence. Full-scene clips should include continuing ambient motion: vary traffic timing, lanes or vehicles, and let a background display reflect the state. Restore its idle pattern during finishing. Limit each uploaded clip to 40 frames or the lower configured limit. This ceiling is a conservative interoperability choice, not a guarantee for every firmware. Native looping avoids continuous frame streaming, but changing clips can show a device loading delay. Do not promise seamless video or native one-shot playback.

## Export and validation

When the user chooses an automatic or motorized prop, preserve the accepted character/body and animate the existing prop layers independently. Keep typing limited to approved fingertip pixels; a visor-only flip does not need arm movement or regenerated character poses. Use foreshortening to suggest a plate turning edge-on when suitable. Verify canonical body, wrist and palm pixels across the whole action. The decker's current start/finish direction is motorized motion in `work-v13`; earlier hand-operated studies are historical experiments.

For a visor or other hand-assisted gesture, replace the original arm/hand position with a clean plate before compositing the moving limb. Keep the other hand in place, and disable typing pixels for the lifted hand. Inspect every native frame for a duplicate hand on the keyboard. For angled monitors, map content across the entire visible glass using its actual outline; a small bright rectangular insert inside a larger static screen can look jarring. Preserve the housing.

Keep hand size and limb lengths consistent through gestures. Fitting an entire arm image to changing shoulder/hand destinations can make it shrink into the background. Use stable pose landmarks; fixed-size limb pieces can suit simple motion, but shoulder movement, cloth folds and newly revealed anatomy may require complete-character key poses drawn together. If using articulated pieces, anchor the upper arm at the actual shoulder and reject unreachable targets instead of stretching. Inspect the whole reach/contact/return sequence. Preserve accepted state artwork exactly when revising only its transitions.

Size generated limbs against the visible arm and hand in the approved base. An occluded far limb can give an unreliable thickness reference; use the foreground limb when chosen by the user. Check actual native opaque sleeve thickness and hand coverage, not just the source bounding box. A tapered source can still look spindly after normalization. Clear the chosen moving limb, retain the other limb, and set compositing depth correctly so the foreground arm can pass in front of the body.

When separate pieces keep failing shoulder, clothing or occlusion review, make a small complete-character pose study before rebuilding the timeline. Draw the torso, shoulder seam, both arms and both hands together. Reconstruct the portions of the stationary limb and backdrop that were hidden in the base; preserving only its previously visible pixels leaves missing anatomy. Keep a cloth band broad through the entire action. Register and composite poses onto the stable scene, then generate deliberate in-betweens at the required frame count. Check face and costume drift as well as anatomy; four held key poses are a study, not a finished 32-frame gesture.

Plan hand-operated props in separate phases: reach the current prop position, grip briefly, carry it through intermediate positions, release only at the destination, then return the hand. Check actual contact and prop travel in native frames; a 32-frame export with moving traffic can still hide a missing character action. If a generated atlas skips a phase, draw focused complete-character gap poses rather than adding holds. Use original-resolution cell extraction for individual edits, and register each supplementary atlas at fixed scene landmarks before compositing.

If arm identity or depth still changes, establish about five complete-character anchors and generate small interval studies between each pair. Subdivide any remaining gaps with smaller studies or focused individual poses. For a foreground hand, the wrist must connect to a visible cuff below the palm and the forearm must overlap the cheek and far arm, never curl around from behind the head. Check the first departures from and final returns to the typing pose. Generated sheets can repeat endpoints or jump across motion despite their requested cell count; curate usable poses after native inspection. Reverse only the character action for an inverse gesture, keeping ambient movement forward.

Read [references/pack-format.md](references/pack-format.md) for the exact shared manifest and CLI. Locate `pixoo-pet.exe` in the workspace, release bundle, or user-specified location. It handles authoring preparation as well as bridge operation; an existing pack needs no image-generation runtime.

Export exact 64x64 frames or 64-pixel cells. A full-scene background stays opaque; a transparent character source is composited onto the manifest background. Save source images and prompts under the requested pack directory. Put previews in a separate subdirectory so directory import does not treat them as animation sources.

Run `validate`, inspect a contact sheet and animated preview when clips exist, and repair any misalignment or unreadable motion. Report normalization of GIF timing. Missing clips are valid and must not cause invented fallback artwork. Keep device IP/token and local hook paths out of distributable art packs. Do not activate a device or change Codex settings merely because artwork was requested.
