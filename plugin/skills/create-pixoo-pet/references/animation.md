# Motion for a fixed 64x64 display

The decker's current start/finish baseline is `pets/decker/revisions/work-v13/`: the approved character continues typing while the visor flips down or up automatically. The owner rejected the cumulative jitter of regenerated hand-operated poses. The optional offline `motorized` path reuses existing visor layers with smooth progression and foreshortening, preserving all body/hand pixels outside the prop/fingertip masks. Screen and traffic timelines continue forward. Generate new raster art only when an existing prop asset is insufficient; complete-character pose studies remain an option for deliberately chosen anatomical gestures, not a requirement for autonomous props.

The display has no pointer, drag position, or unread-message UI. Build actions that read from pose, monitor color, and a few distinct pixels. A complete room can work if most of it stays still.

The bridge selects one full clip rather than composing layered activities.

Use at least 16 frames for short actions and 24-32 frames for sustained idle or working loops, within the 40-frame upload ceiling. At 83 ms per frame, a 32-frame loop lasts 2.656 seconds. Intentional holds between key poses are useful, but plan motion over the whole timeline; repeating an eight-frame sequence four times does not make its motion longer. Do not shorten an approved loop merely to reduce upload time. Each cell is 64x64. Cell count and ordering must agree with the manifest.

For a room scene, preserve the approved base as a fixed layer. Limit scrolling to the monitor's full visible interior, leaving its bezel and perspective unchanged. Trace the actual angled glass outline instead of animating only a small rectangle within it. For typing, animate fingertip flexion while pinning wrists and palms. For deliberate gestures, clear the lifted arm and hand's original position before adding one registered transparent limb layer; keep the other hand fixed and inspect all frames for duplicate keyboard hands. Small background actions, such as a blinking terminal cursor or a distant passing vehicle, can occupy separate masks. A broad rectangular copy of generated hands or a whole monitor can translate the object with the motion and should not be used.

Generated key poses may drift even with explicit constraints. Register the source poses against fixed anatomical landmarks before extracting fingertip pixels, and composite only the allowed regions onto the canonical base. Inspect the native frames and enlarged hand crops; check that every pixel outside the allowed regions remains identical to the base. Check the last-to-first transition as well. For GIF previews, use a shared palette across frames so quantization does not make the fixed background flicker. The bridge's PNG sprite source retains full RGB color.

Keep limb lengths and hand size stable during a reach. Whole-arm similarity transforms can vary scale dramatically when generated poses have different shoulder-to-hand distances, making the arm appear to recede. Use consistently sized poses or generated upper sleeve, fore sleeve and hand textures normalized once and rotated at fixed joints. For an articulated gesture, record bone lengths and transform scale, maintain a consistent elbow branch, and keep wrist targets within the fixed reach. Small pixel-coverage changes from nearest-neighbor rotation differ from deliberate shrinking. Review the entire sequence, including keyboard departure, visor contact and return. When the user accepts a working loop but requests transition changes, preserve its native RGB and GIF palette instead of regenerating it.
